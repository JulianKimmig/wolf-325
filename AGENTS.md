# coding
On a coding task strictily follow these rules.
Most important, never delete files, which you should not touch or which dont belong to your current task. If you are not 100% they should be deleted, dont, just mention them and leave this to the user!!!

## basic
- Build modular first. No code files longer than 300 lines of code! Documentation, plans and example files and notebooks etc. can be as long as needed, but src code files must be modular.
- Keep source layout as flat as possible until related changes become hard to find or reason about. When structure is needed, group files by cohesive responsibility, feature, or ownership boundary so related behavior, state, integrations, and helpers stay close together.
- Think ahead! Do not write code that you know will need to be changed later without planning for that change now. So keep entrypoints stable and isolate logic into smaller modules from the start!
- Do not limit yourself due to the LOC limit! If a task requires more code, split it into multiple files/modules/functions
- The LOC limit does not apply to text files, autogenerated files and special files where a single file is expected (e.g. migration files)
- Do not add default fallbacks during development phase. Is something fails, let it fail, so we can fix it!
- Do not leavy empty try-catch blocks anywhere!
- Do not reinvent the wheel! Use open source, self-hosted libraries when needed. Ask the user, and help them qualify their selection.
- Every file should have an initial file docstring and every class, function method etc should also have a detailed docstring, where arguments and returntypes are explained. the layout should follow the guidelines of the respective programming language.

## structure

### Choosing Flat vs. Nested Folders
Use the structure that makes ownership obvious. Keep a folder flat only while its files form one clear concept and remain easy to scan. Add subfolders as soon as files split into distinct responsibilities, layers, lifecycle stages, or change patterns.
Prefer nesting when files naturally group by purpose, such as contracts/, runtime/, ui/, tests/, fixtures/, validation/, or adapters/. Avoid nesting only when it adds empty ceremony, such as one-file folders with no real boundary.
Do not decide by file count alone. Decide by whether the structure helps a new developer quickly understand where behavior belongs.

# architecture

## system-of-record
Before changing, adding, moving, or deleting code, identify which system-of-record entries describe the affected structure, behavior, contracts, dependencies, workflows, or architectural boundaries. Consult and update those entries as part of the change, not as a separate cleanup task.

Use this default layout unless the repository already defines a better one:

- `.docs/ARCHITECTURE.md` — top-level architecture, package/layer boundaries, allowed dependencies
- `.docs/code-relationships.md` — relationships between modules, schemas, generated files, tests, configs, APIs, UI, CLI, jobs, and external integrations
- `.docs/domains/<domain>.md` — domain concepts, invariants, workflows, and ownership of behavior
- `.docs/contracts/<contract>.md` — public APIs, data schemas, events, config formats, storage formats, and compatibility rules
- `.docs/workflows/<workflow>.md` — operational workflows, validation steps, release/migration procedures
- `.docs/decisions/<id>-<topic>.md` — durable architectural or product decisions and their rationale
- `.docs/generated/` — generated reference documentation; regenerate via tooling, do not hand-edit unless fixing the generator
- `.docs/plans/active/` — execution plans for complex or risky changes, whenever plans are created put them here
- `.docs/plans/completed/` — completed plans with final decisions and relevant follow-ups. if a plan from active is complete, move it here

If a required system-of-record entry is missing, stale, ambiguous, or structurally misplaced, do not ignore the gap. Create or repair the entry carefully at the correct structural location. For non-trivial entries, delegate the documentation task to a high-reasoning sub-agent with necessary information and this instruction: inspect the whole relevant codebase area, infer the actual structure from code and tests, avoid inventing unsupported rules, write the minimal durable record, and cross-link all affected files, tests, contracts, and workflows.

Every code change must leave the system of record accurate at the relevant structural positions. Do not append a generic “task completed” note. Update the specific architecture, relationship, contract, domain, workflow, decision, generated, or plan document that owns the changed fact.
